# 가상 금융 업무 AI Agent (LangGraph 미니 프로젝트)

은행 앱의 계좌 조회, 거래내역 조회, 이체, 카드 관리 같은 기능을 **사용자의 자연어 요청**으로 처리하는 AI Agent입니다.
LangGraph로 supervisor가 요청을 분석해 담당 agent로 보내고, 데이터를 바꾸는 이체는 `interrupt`로 **승인·거절**을 받은 뒤에만 실행합니다.
데이터는 실제 은행이 아니라 JSON 파일(`data/data.json`)로 만든 가상 데이터입니다.

## 구현한 기능

| 기능 | 요청 예시 | 비고 |
|---|---|---|
| 계좌 목록·잔액 조회 | "내 계좌 잔액 알려줘" | 계좌를 지목하지 않으면 전체를 나열 |
| 잔액 합산 | "내 계좌에 총 얼마 있어?" | 잔액 조회 tool이 `total_balance`를 코드로 계산해 반환(LLM이 직접 더하지 않음) |
| 거래내역 조회 | "이번 달 생활비 출금 내역 보여줘" / "5만 원 이상 결제한 내역 찾아줘" | 기간·금액·유형·카드 결제 필터, 최근순, 건수·유형별 합계, 카드 결제는 카드 이름 표시 |
| 내 계좌 간 이체 | "저축에서 여행 자금으로 50만 원 이체해줘" | 승인 후 잔액·거래내역·처리 기록을 한 번에 저장 |
| 조건부 이체(잔액 유지) | "저축에 30만 원만 남기고 여행 자금으로 이체해줘" | 이체액 = 잔액 − 남길 금액을 코드가 계산. 실행 직전 잔액이 바뀌면 다시 계산해 재승인 요청 |
| 분할 이체 | "생활비에서 저축으로 10만 원, 여행 자금으로 20만 원 나눠서 이체해줘" | 한 출금 계좌 → 여러 입금 계좌. legs 전체를 한 번에 저장(일부만 반영되지 않음) |
| 승인·거절 | 승인 화면에서 "승인" / "거절" | `interrupt`로 멈추고 `Command(resume=...)`으로 재개 |
| 자연어 승인·취소 | "응, 진행해" / "취소할게" | 응답 해석은 LLM, 실행 여부의 최종 규칙은 코드 |
| 승인 전 수정 | "아니, 5만 원만" / "저축 말고 여행 자금으로" | 금액·출금 계좌·입금 계좌를 수정하고 전체 화면을 다시 보여준 뒤 새로 승인받음. **정액 이체만 지원**(조건부·분할 이체는 수정 없이 승인/거절만) |
| 계좌 별명 변경 | "여행 자금 계좌 이름을 휴가비로 바꿔줘" | 대상 계좌·새 별명을 확인하고 승인 후 저장. 별명은 앞뒤 공백 제거 후 1~20자, 본인의 다른 계좌와 중복 불가 |
| 카드 조회 | "내 카드 목록과 상태 보여줘" | 카드 이름·ID·종류(신용·체크)·상태(사용 가능/일시 잠금/분실 정지) 조회 |
| 카드 분실 정지 | "생활비 카드 잃어버렸어. 정지해줘" | 사용 가능·일시 잠금 카드 모두 분실 정지 가능. 승인 후 처리 |
| 카드 일시 잠금 | "생활비 카드를 잠깐 잠가줘" | 사용 가능한 카드만 잠금 가능. 승인 후 처리 |
| 카드 잠금 해제 | "생활비 카드 잠금 풀어줘" | 일시 잠금된 카드만 해제 가능(분실 정지된 카드는 해제 불가). 승인 후 처리 |
| 카드 재발급 신청 | "잃어버린 생활비 카드를 집으로 재발급받고 싶어" | 분실 정지된 카드만 신청 가능. 배송지는 등록된 주소(집/회사) 중 선택. 취소되지 않은 신청이 이미 있으면 새로 만들지 않고 안내 |
| 재발급 신청 조회 | "카드 재발급 신청 상태 알려줘" | 신청별 배송지·처리 상태 조회. 대상이 불명확하면 되묻고, 없으면 기록 없음을 안내 |
| 재발급 신청 수정·취소 | "재발급 배송지를 회사로 바꿔줘" / "재발급 신청 취소해줘" | **접수 상태일 때만** 가능(제작 중·배송 중이면 불가) |
| 정지 후 재발급 | "생활비 카드를 잃어버렸어. 정지하고 재발급해줘" | 분실 정지 승인 → 이어서 재발급 승인까지 한 번의 요청에서 순차 처리(각각 따로 승인받음). 이미 분실 정지된 카드면 정지 단계 없이 바로 재발급 승인으로 진행 |
| 추가 질문 | "이체해줘" | 빠진 항목(출금 계좌·입금 계좌·금액)을 되묻고 다음 답변으로 이어감 |
| 지원하지 않는 요청 안내 | "미납 청구서 납부해줘" | 정해진 안내문으로 답함 |

구현하지 않은 기능(청구서, 후속 결과 조회, 재시작 복구 등)은 아래 [한계와 개선하고 싶은 점](#한계와-개선하고-싶은-점)에 적었습니다.

## 구조

```
사용자 요청 → START → supervisor ─┬→ account_agent              (잔액·거래내역 조회)       → END
                                  ├→ transfer_agent             (내 계좌 간 이체)          → END
                                  ├→ nickname_agent             (계좌 별명 변경)           → END
                                  ├→ card_agent                 (카드·재발급 신청 조회)     → END
                                  ├→ card_status_agent          (분실 정지/일시 잠금/해제)  → END
                                  ├→ reissue_agent              (재발급 신청/수정/취소)     → END
                                  ├→ card_lost_and_reissue_agent (분실 정지 → 재발급 순차)  → END
                                  └→ unsupported                (지원하지 않는 요청 안내)    → END
```

- **account_agent**: `account_call_model`(어떤 tool을 부를지 LLM이 판단) ↔ `tools`. `tools` 노드는 `ToolNode(account_tools, wrap_tool_call=enforce_owner)`로 구성되어, tool 실행 직전 `enforce_owner` middleware가 tool 호출의 `owner_id`를 로그인한 사용자의 값으로 강제로 바꿉니다(수업에서 배운 `wrap_tool_call` 방식).
- **transfer_agent**: `transfer_extract`(대화에서 이체 정보 추출, 정액/조건부(잔액 유지)/분할 세 유형 판단) → `transfer_validate`(검증) → `transfer_approve`(`interrupt`로 승인 화면) → `transfer_interpret`(응답 해석) → `transfer_execute`(재검증 후 저장). 응답이 수정이면 `transfer_approve`로 되돌아가는 순환이 있고, 조건부 이체는 실행 직전 잔액이 바뀌면 `transfer_execute`에서도 `transfer_approve`로 되돌아갑니다.
- **nickname_agent**: `nickname_extract`(대상 계좌·새 별명 추출) → `nickname_validate`(검증) → `nickname_approve`(`interrupt`로 승인 화면) → `nickname_interpret`(승인/거절/불명확 해석) → `nickname_execute`(재검증 후 저장). transfer_agent와 같은 승인·재검증 구조를 재사용하되, 자연어 수정은 지원하지 않습니다(승인/거절만).
- **card_agent**: `card_call_model` ↔ `tools`(카드 조회·재발급 신청 조회 tool 2개, 같은 `enforce_owner`). account_agent와 같은 조회 전용 ReAct 구조입니다.
- **card_status_agent**: 분실 정지/일시 잠금/잠금 해제 세 가지를 `kind`로 분기해서 처리하는 하나의 승인 흐름(nickname_agent와 같은 구조). 자연어 수정은 지원하지 않습니다.
- **reissue_agent**: 재발급 신청/배송지 변경/신청 취소 세 가지를 `kind`로 분기해서 처리하는 승인 흐름.
- **card_lost_and_reissue_agent**: `card_status_agent`(분실 정지, 이미 실행 중인 카드가 있으면 재발급으로 건너뜀)를 실행한 뒤, 성공했을 때만 이어서 `reissue_agent`(재발급 신청)를 실행하는 서브그래프. 두 단계 모두 각각 따로 승인받습니다.
- **역할 분담 원칙**: 자연어 해석은 LLM이, 계산·필터·정렬·검증·데이터 변경은 코드가 합니다.

자세한 설계와 변경 이유는 [`설계초안.md`](설계초안.md)와 [`최종설계자료.md`](최종설계자료.md)에 있습니다.

## 실행 방법

### 준비물

- Python 3.13 이상, [uv](https://docs.astral.sh/uv/)
- Google Gemini API 키(Google AI Studio에서 발급)

### 1. 설치

```bash
uv sync
```

### 2. `.env` 만들기 (프로젝트 루트)

API 키는 저장소에 포함되어 있지 않습니다(`.gitignore`로 제외). 프로젝트 루트에 `.env` 파일을 만들고 아래 두 줄을 넣으세요.

```
GEMINI_API_KEY=발급받은_API_키
GEMINI_MODEL=사용할_Gemini_모델_이름
```

`GEMINI_MODEL`은 수업에서 사용한 Gemini 모델 이름을 그대로 쓰면 됩니다. `.env`가 없으면 `graph`를 불러오는 단계에서 `model` 값이 `None`이라는 오류가 납니다.

### 3. 실행

프로젝트 루트에서 실행합니다.

```bash
uv run python src/main.py
```

`나:` 프롬프트에 요청을 입력합니다. 종료는 `quit`(또는 `exit`, `종료`)입니다. 이체는 승인 화면이 나오면 `승인`, `거절` 또는 수정할 내용을 입력합니다.

### 데이터 초기화

`main.py`에서 이체를 승인하면 `data/data.json`이 실제로 바뀝니다. 초기 상태로 되돌리려면 원본을 다시 복사합니다.

```bash
uv run python -c "import sys; sys.path.insert(0, 'src'); import data_store; data_store.reset_data()"
```

### 테스트

```bash
uv run python src/test_transfer.py
uv run python src/test_transfer_extended.py
uv run python src/test_transactions.py
uv run python src/test_enforce_owner.py
uv run python src/test_nickname.py
uv run python src/test_card.py
```

여섯 테스트는 LLM과 API 키가 필요 없고, `test_transfer.py`·`test_transfer_extended.py`·`test_nickname.py`·`test_card.py`는 원본의 임시 복사본으로만 실행하므로 `data.json`을 바꾸지 않습니다. `test_transfer_extended.py`는 조건부(잔액 유지)·분할 이체를, `test_nickname.py`는 계좌 별명 변경을, `test_card.py`는 카드 상태 변경·재발급 신청·정지 후 재발급을 검증합니다.

기준일은 **2026-09-20으로 고정**되어 있고(초기 데이터의 마지막 거래일), 로그인 사용자는 `user-001`(계좌 3개)입니다. 초기 데이터 기준의 기대 결과입니다.

| 이번 주 거래내역 알려줘 | 9/14~9/20, 6건(입금 130,000 / 출금 85,700) |
| 지난달 거래내역 알려줘 | 8월, 2건(입금 300,000 / 출금 52,000) |

| 저축에서 여행 자금으로 50만 원 이체해줘 → `승인` | 저축 1,780,000 / 여행 자금 890,000, 처리 번호 req-001 |

| 이체해줘 → `생활비에서 저축으로 10만 원이요` | 부족한 정보를 되묻고 답변으로 이어서 승인 화면까지 진행 |
| 저축에 30만 원만 남기고 여행 자금으로 이체해줘 → `승인` | 이체액 1,980,000원 계산(2,280,000 − 300,000), 저축 300,000 / 여행 자금 2,370,000 |
| 생활비에서 저축으로 10만 원, 여행 자금으로 20만 원 나눠서 이체해줘 → `승인` | 생활비 1,131,800 / 저축 2,380,000 / 여행 자금 590,000, 처리 번호 2건 |
| 여행 자금 계좌 이름을 휴가비로 바꿔줘 → `승인` | 별명이 "여행 자금"에서 "휴가비"로 바뀜 |
| 내 카드 목록과 상태 보여줘 | 생활비 카드(체크카드, 사용 가능) / 여행 카드(체크카드, 사용 가능) |
| 생활비 카드를 잠깐 잠가줘 → `승인` | 생활비 카드 상태가 일시 잠금으로 바뀜 |
| 생활비 카드를 잃어버렸어. 정지하고 재발급해줘 → `승인` → (배송지 물으면) `집으로 보내줘` → `승인` | 카드가 분실 정지된 뒤 이어서 재발급 신청까지 완료(신청 번호 부여) |
| 재발급 배송지를 회사로 바꿔줘 → `승인` | 접수 상태인 신청의 배송지가 회사로 바뀜 |

## 실패 상황 동작 확인 결과

직접 선정한 실패 상황을 실제 LLM으로 실행해 확인한 결과입니다. 이체 계열은 임시 데이터 복사본으로 실행했고 실제 `data.json`은 바뀌지 않았습니다.

| 상황 | 요청 | 동작 |

## 알아둘 점

- **`main.py`는 `data/data.json`을 바꿉니다.** 이체를 승인하면 파일이 갱신되므로, 같은 상태로 다시 시험하려면 위 [데이터 초기화](#데이터-초기화)를 실행하세요.
- **이체 거래 시각**은 고정 기준일(2026-09-20)에 실행 시점의 현재 시각을 붙여 기록합니다.
- 조회에서 사용자가 시작일·종료일을 거꾸로 말하면(예: "9월 30일부터 9월 1일까지") LLM이 tool을 부르기 전에 날짜를 바로잡아 조회하고 해석한 기간을 안내합니다. tool 자체의 "시작일이 종료일보다 늦습니다" 오류는 단독 테스트에서만 확인됩니다.
- 대화 기록은 `InMemorySaver`에 있어서 프로그램을 끄면 사라집니다.

## 한계와 개선하고 싶은 점

- 카드 자체의 제작·배송 진행(실제 배송 조회 등), 청구서(조회·납부·일괄 납부), 후속 결과 조회("아까 이체가 됐어?"), 대화 대상 확인은 구현하지 않았습니다. 현재는 "지원하지 않는다"고 안내합니다.
- 조건부(잔액 유지) 이체, 분할 이체, 계좌 별명 변경, 카드 상태 변경, 재발급 신청·취소는 **승인 화면에서 자연어 수정을 지원하지 않습니다**(정액 이체만 수정 가능). 수정하려는 응답은 승인/거절만 받고, 이해하지 못한 응답으로 처리해 다시 묻습니다. 재발급 신청의 배송지 자체를 바꾸는 것은 별도 명령("재발급 배송지를 회사로 바꿔줘")으로 지원합니다.
- 분할 이체는 입금 계좌 중복(같은 계좌로 두 번 나눠 보내기)을 막지 않습니다.
- 재발급 신청은 카드당 취소되지 않은 신청 1건으로 제한하지만, 여러 카드를 한 번에 재발급 신청하는 것은 지원하지 않습니다(카드 1개씩 요청).
- 카드 재발급의 제작 중·배송 중 진행(실제 배송 추적)은 구현 범위 밖이라, 그 상태들은 테스트 코드가 직접 주입해서만 확인합니다.
- **재시작·장애 복구**: 승인 대기 중인 이체·별명 변경·카드 처리가 프로그램 종료와 함께 사라집니다. SQLite 등 영속 checkpointer가 필요합니다(안전을 위해 이전 승인만으로 자동 실행하지는 않습니다).
- `requests`에는 **완료된 처리만** 기록합니다(이체·별명 변경·카드 상태 변경 공통). 거절·실패도 남겨야 후속 결과 조회를 만들 수 있습니다.
- 응답 해석과 라우팅은 LLM에 의존합니다. 승인 같은 위험한 결정은 코드가 규칙으로 막지만, 라우팅 정확도는 프롬프트에 좌우됩니다. 라우팅은 대표 문장 12개를 3회씩 반복해 확인했으나 모든 표현을 보장하지는 않습니다.
- API 키를 저장소 밖 `.env`에서 읽습니다. `.env`가 없을 때의 오류 메시지가 불친절합니다.

## AI 활용 고지

이 프로젝트는 Claude(Anthropic)와 대화하며 설계·구현했습니다.

- **설계**: 결정 지점과 선택지, 피드백은 Claude가 제시했고 선택과 결정은 내가 했습니다. 이체의 1·2차 초안과 승인 흐름 초안은 내가 직접 썼지만(원문은 `설계초안.md`에 보존), 일부는 Claude의 제안을 반영해서 다시 쓴 것입니다.
- **구현**: 코드는 대부분 Claude가 작성했습니다. 나는 코드를 읽고 이해한 뒤 질문했고, 이체와 승인 흐름 구현은 설계를 위임했습니다.
- **검증**: 테스트는 Claude가 작성·실행했고, 나는 `main.py`로 여러 요청을 직접 실행해 결과를 데이터와 대조했습니다.

자세한 내용은 `설계초안.md`의 "AI 활용 내역"에 있습니다.
